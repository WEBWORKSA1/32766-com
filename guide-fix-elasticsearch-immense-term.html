Fix “immense term … max length 32766”

The error means one value you're indexing as a single term is larger than 32,766 bytes. Here's why it happens and five ways to fix it, from a one-line mapping change to a proper redesign.

32766.com editorial · Updated November 19, 2026 · 9-minute read

In short
  • Lucene caps every indexed term at 32,766 bytes of UTF-8.
  • A keyword field indexes the whole value as one term, so long strings break it.
  • ignore_above counts characters, not bytes — set it conservatively.
  • Best long-term fix: map long text as text, and index a hash or prefix for exact matching.

What the error looks like

illegal_argument_exception: Document contains at least one immense term in field="body.keyword"
(whose UTF8 encoding is longer than the max length 32766), all of which were skipped.
Please correct the analyzer to not produce such terms. The prefix of the first immense term is: '[60, 112, 62, …]...'
caused_by: max_bytes_length_exceeded_exception: bytes can be at most 32766 in length; got 43053

The byte list in the message is the start of the offending value in decimal (60 = “<”, 112 = “p”) — handy for finding which document caused it. The “got” number is the value's size in bytes.

Why it happens

Dynamic mapping turns every new string into a text field with a .keyword sub-field. Dynamic templates usually set ignore_above: 256 on that sub-field, but custom mappings, flattened fields, explicit keyword fields, and analyzers that don't split (e.g. the keyword tokenizer with a normalizer) all produce whole-value terms. HTML bodies, base64 attachments, serialized JSON and long log lines are the usual culprits.

Fix 1 — Add or lower ignore_above

PUT my-index/_mapping
{
  "properties": {
    "body": {
      "type": "text",
      "fields": { "keyword": { "type": "keyword", "ignore_above": 8191 } }
    }
  }
}

Values longer than the threshold (in characters) aren't indexed in the keyword sub-field but stay in _source. Because UTF-8 can use up to 4 bytes per character, 32,766 ÷ 4 = 8,191 characters is the threshold that is always byte-safe. Elastic's documentation notes that some newer columnar index modes keep values instead of dropping them, so ignore_above no longer protects you there — check the docs for your version and index mode.

Fix 2 — Don't use keyword for long text

If nobody sorts, aggregates or filters on the exact full value, drop the keyword sub-field and keep only text. Analyzed text is split into many small terms and never hits the limit (unless an analyzer emits a giant token — add a length or truncate token filter as a guard).

Fix 3 — Index a hash for exact matching

Need to deduplicate or look up by exact value? Store a fixed-size fingerprint (SHA-256 is 64 hex characters) in a keyword field and query that. You can compute it in your application or with an ingest pipeline:

PUT _ingest/pipeline/fingerprint-body
{ "processors": [ { "fingerprint": { "fields": ["body"], "target_field": "body_hash", "method": "SHA-256" } } ] }

Fix 4 — Truncate safely before indexing

If a prefix is good enough (e.g. sorting by the first 200 characters), truncate in the application or with a script processor. Truncate by bytes without splitting a character — our truncator and byte counter show how, and the splitter's Lucene preset chunks values into 32,766-byte pieces.

Fix 5 — Use a binary or non-indexed field

For attachments and blobs you never search, use "type": "binary" or set "index": false (and often "doc_values": false) so the value is stored but never turned into a term.

Prevent it next time

  • Validate byte length at ingestion: len(value.encode('utf-8')) <= 32766.
  • Use explicit mappings or dynamic templates for long-text fields.
  • Alert on bulk-response item errors instead of ignoring partial failures.
  • Remember Solr has the same limit for StrField values.
