Token rules of thumb

  • 1 token ≈ 4 characters of English ≈ ¾ of a word
  • 100 tokens ≈ 75 words; 1,000 words ≈ 1,300–1,400 tokens
  • Code, JSON, numbers and URLs use more tokens per character
  • Chinese, Japanese and Korean often use ≈1 token per character or more
  • The context window holds the prompt and the answer

How the estimate works

Language models read text as tokens — word pieces from a fixed vocabulary. Every provider uses its own tokenizer, so the same paragraph can be 100 tokens on one model and 115 on another. This tool blends a character-based estimate (characters ÷ 4) with a word-based one (≈1.33 tokens per word, plus punctuation) and counts CJK characters individually. For ordinary English it typically lands within ±15% of real tokenizers. It's built for budgeting, not billing.

Leave headroom

Reserve the maximum answer length you'll request, add a margin for system prompts and tool definitions, and don't plan to fill the window. Many models get less reliable at recalling details deep in very long contexts, so retrieval (sending only the relevant chunks) often beats stuffing everything in. FAQ

Why not an exact count?

Exact counts need each model's tokenizer vocabulary (several megabytes each), and some providers don't publish theirs. Your provider's API usually returns exact usage per request — use that for billing.

Does whitespace cost tokens?

Yes. Runs of spaces, indentation and blank lines are tokens too. Minifying JSON and trimming whitespace with the text cleaner can cut prompt size noticeably.

What chunk size should I use for RAG?

A common starting point is 300–800 tokens with 10–20% overlap, then tune with real retrieval tests. The text splitter has a 512-token preset.
