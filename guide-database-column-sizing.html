Sizing columns for multilingual text

“VARCHAR(255) is enough” is true until a customer writes in Japanese, pastes emoji, or you add an index. Here's how to size text columns in bytes.

32766.com editorial · Updated November 19, 2026 · 6-minute read

Know your unit

  • MySQL VARCHAR(n) — n is characters, but storage, row size (65,535 bytes shared) and index keys (3,072 bytes for InnoDB DYNAMIC) are bytes. With utf8mb4, assume 4 bytes per character.
  • PostgreSQL varchar(n) — n is characters; B-tree index entries max out around 2,704 bytes.
  • SQL Server varchar(n) — n is bytes (≤8,000); nvarchar(n) — byte-pairs (≤4,000). Index keys: 900 bytes clustered, 1,700 nonclustered.
  • Oracle VARCHAR2(n BYTE|CHAR) — specify CHAR semantics explicitly; the column still can't exceed 4,000 bytes (32,767 with extended strings).

A sizing worksheet

  1. Decide the maximum visible length you'll accept (e.g. a 120-character display name).
  2. Multiply by 4 for the worst-case bytes in utf8mb4 (480).
  3. Check against any index you'll build on the column; use a prefix index or a hash column if it doesn't fit.
  4. Validate at the API with the same unit — graphemes for UX, bytes for storage.

Long text that must be unique

Add a generated column with a hash (e.g. SHA-256) and put the unique index on that. It's fixed-size, fast, and avoids every key-length limit — the same trick that fixes Lucene's 32,766-byte term error.

-- MySQL 8
ALTER TABLE pages ADD url_hash BINARY(32) AS (UNHEX(SHA2(url, 256))) STORED, ADD UNIQUE KEY (url_hash);
-- PostgreSQL
CREATE UNIQUE INDEX ON pages (md5(url));

Always utf8mb4

MySQL's legacy utf8 can't store 4-byte characters, so emoji fail or are mangled. Use utf8mb4 for the server, database, tables and connection.
